\begin{abstract}
Code-review agents can agree on a plausible finding even when the cited code does not support it. We study whether a machine-checkable evidence requirement reduces this \emph{false consensus}. Evidence-Verified Adversarial Review (\evar) adds a structured receipt---file, lines, expected observation, falsification condition, and optionally a bounded command---to a reviewer/critic protocol. A deterministic verifier must accept the receipt before the finding can become actionable. We compare ordinary adversarial review (AR), textual evidence (AR-Text), and \evar-Hard under matched prompts, cases, and call budgets. The untouched Human PR 20 holdout contains 120 decisions over temporal pairs derived from ten public review comments. With GPT-4.1-mini, AR-Text and \evar-Hard tie at \fcr/\scr=.200/.700; with GPT-4.1, \evar-Hard scores .300/.600 versus .200/.700 for AR-Text. A 180-decision OpenAI model extension is likewise heterogeneous; a separate 180-attempt cross-provider study completes only seven of fifteen protocol cells, exposing schema and serving failures. Across 900 fully completed matched decisions, deterministic verification changes the safety--retention operating point but does not dominate textual evidence. Its robust benefit is procedural: every actionable \evar finding carries an inspectable machine result, while invalid evidence becomes an explicit failure rather than silent agreement.
\end{abstract}

\section{Introduction}

Reviewer-critic systems use a second model call to challenge or refine a first model's answer. Iterative self-feedback and multi-agent debate can improve generation and reasoning \cite{selfrefine,debate}, but textual agreement is not independent evidence. In code review, two agents can converge on the same plausible interpretation of code while both overlook the observation that would falsify it.

Consider a documentation finding from Black pull request 5272 in our holdout. A human reviewer asked that an internal explanation involving \texttt{hug\_power\_op} and cloned leaves be replaced with a concise user-facing changelog entry. The same claim is true at the reviewed commit and false after the merge edit. A textual critic can accept the finding in either snapshot because the wording remains plausible. An evidence receipt must instead identify the exact changelog lines present in that snapshot. The example captures our unit of analysis: not whether a model can discover every issue in a pull request, but whether one candidate finding deserves to cross an actionability boundary.

\evar changes the acceptance rule. A reviewer submits a structured evidence receipt; a deterministic verifier checks a source location or executes a bounded witness; and only a verified receipt can become actionable. We ask whether that external gate reduces false consensus without suppressing supported findings.

We organize the study around three research questions:
\begin{description}
  \item[RQ1 (decision quality).] Does deterministic evidence verification reduce unsupported actionable findings without an unacceptable loss of supported findings?
  \item[RQ2 (model sensitivity).] Does the safety--retention operating point persist across model capability and cost tiers?
  \item[RQ3 (auditability).] Which protocol failures become mechanically observable when actionability requires a verified receipt?
\end{description}
These questions deliberately separate predictive performance from procedural assurance. A protocol can fail to dominate on \fcr and \scr while still making its acceptance path easier to inspect. Conversely, a high receipt-verification rate need not imply that the submitted evidence is relevant to the claim.

Our contributions are:
\begin{enumerate}
  \item \textbf{Protocol:} a structured evidence receipt and deterministic gate that make acceptance conditions externally inspectable;
  \item \textbf{Benchmark:} a temporally paired holdout built from public human review comments at reviewed and merged commits;
  \item \textbf{Evidence:} matched AR, AR-Text, and \evar-Hard experiments showing a reproducible, model-sensitive safety--retention tradeoff rather than universal dominance; and
  \item \textbf{Artifact:} frozen inputs, transcripts, result manifests, and judge-free audits for 900 completed matched decisions, plus canonical accounting for 180 cross-provider attempts with failures retained explicitly.
\end{enumerate}

\section{Related Work}

\subsection{Reflection, critique, and debate}

Self-Refine uses model-generated feedback to iteratively improve a model's output \cite{selfrefine}. Reflexion incorporates linguistic feedback into an episodic memory rather than updating model weights \cite{reflexion}. Multi-agent debate has similarly improved reasoning and factuality through textual deliberation \cite{debate}. These methods motivate the AR baselines but do not, by themselves, make agreement independent evidence. The same model family can reproduce a shared misconception across reviewer and critic roles.

Prior work also questions whether intrinsic self-correction is reliable without external feedback. CRITIC couples model critique to tool interactions and reports gains across question answering, program synthesis, and toxicity reduction \cite{critic}. \evar adopts the external-feedback premise but narrows both the task and the acceptance rule: the system judges a pre-specified code-review claim, and a deterministic receipt check is a necessary gate rather than optional context for another revision.

\subsection{Tool-using software-engineering agents}

SWE-agent shows that the interface between a model and a computer materially affects software-engineering performance \cite{sweagent}. Executable feedback can reveal failures that are invisible in a textual conversation, but unrestricted agent execution also introduces a large design surface. \evar uses a deliberately narrow interface: structural source checks or a shell-free verification process launched from the benchmark fixture under a timeout. This makes the acceptance boundary easier to audit, at the cost of incomplete coverage for repository-scale semantic claims. The current prototype does not claim operating-system isolation; production use requires a disposable container or stronger sandbox.

\subsection{Code review as a sociotechnical practice}

Modern code review is not reducible to defect detection. Interviews at Microsoft identify knowledge transfer, alternative solutions, and team awareness alongside finding defects \cite{bacchelli-bird}; Google's review process likewise emphasizes a lightweight, tool-mediated practice embedded in development rather than a standalone classifier \cite{sadowski}. This broader view constrains our claims. FCR and SCR measure the fate of a supplied technical claim, not whether a generated comment is timely, understandable, or useful to a team. Industrial studies of deployed automated review systems further show why adoption and workflow outcomes require separate measurement \cite{automated-practice,rovodev}. We therefore treat developer utility as future work rather than inferring it from benchmark accuracy.

\subsection{Automated code review and benchmarks}

CodeReviewer pre-trains on code changes and review activities, evaluating quality estimation, comment generation, and refinement \cite{codereviewer}. That line of work asks whether a system can generate or improve reviews. Our task begins later in the pipeline: a candidate claim already exists, and the system must decide whether the repository snapshot supports actionability.

Hybrid review systems combine learned generation with rule-based analyzers to recover some precision without surrendering broad issue coverage \cite{hybrid-static}. \evar shares the motivation but assigns the deterministic component a different role: it validates the submitted observation and controls actionability; it neither generates a parallel comment nor establishes semantic relevance by itself.

Software-engineering benchmarks increasingly ground tasks in public development history. SWE-bench uses real GitHub issues and pull requests and demonstrates the need for repository context and executable environments \cite{swebench}. SWE-PRBench evaluates code-review models against pull-request feedback and reports limited detection of human-flagged issues \cite{sweprbench}. Our task is narrower: a candidate claim is given, and the system must decide whether it remains actionable under the supplied repository snapshot.

SWR-Bench makes a complementary choice: it evaluates 1,000 complete pull requests with full-project context and structured ground truth, then asks whether generated reviews cover the reported issues \cite{swrbench}. EVAR is smaller and deliberately different. It does not score open-ended issue discovery; it fixes one candidate claim and asks whether that claim can cross an auditable evidence boundary. That trades breadth for a clean test of false consensus and lets us report why a finding was accepted, rejected, or mechanically unverifiable. A future larger benchmark should combine EVAR's receipt-level audit with the PR-scale context and manual verification used by SWR-Bench.

ContextCRBench reaches a different scale, with context-enriched entries for quality assessment, localization, and comment generation \cite{contextcrbench}. Its emphasis on issue context and fine-grained localization reinforces an important external-validity limit here: EVAR's focused excerpts isolate the verification question, but they cannot substitute for evaluating complete pull requests with developer intent.

\section{Protocols}

The reviewer always returns exactly one schema-constrained receipt. The protocols differ in what happens to that receipt before criticism.

An \evar receipt contains the claim, evidence type and role, file and line range, optional verification command, expected observation, and falsification condition. Structural evidence is accepted only by exact source matching after conservative cleanup of display-only line numbers and Markdown fences. Behavioral witnesses must exit successfully and print a designated pass marker only when the claim is supported. The verifier does not use semantic fuzzy matching or model judgment.

In every run, the reviewer sees the candidate claim and repository snapshot but not the benchmark label. AR passes the submitted claim and receipt fields to a critic but labels verification as unused. AR-Text converts the receipt into a textual-evidence object (file, range, quoted or paraphrased support, and falsification condition) without executing it. \evar-Hard verifies the receipt before the critic call. The critic still receives failed verification, but its acceptance cannot override the hard gate. This makes three failure modes visible separately: misunderstanding the claim, citing evidence that does not verify, and presenting a verified observation that is irrelevant to the claim.

\subsection{Actionability semantics}

Let $c$ be a candidate claim, $d\in\{\texttt{ACCEPT},\texttt{REJECT}\}$ the critic decision, and $v\in\{\texttt{VERIFIED},\texttt{FAILED}\}$ the verifier outcome. The final gates are
\[
A_{\mathrm{AR}}(c)=\mathbf{1}[d=\texttt{ACCEPT}],\qquad
A_{\mathrm{EVAR}}(c)=\mathbf{1}[d=\texttt{ACCEPT}\land v=\texttt{VERIFIED}].
\]
AR-Text shares the AR gate but supplies textual evidence to the critic. The distinction is therefore not whether evidence appears in the dialogue; it is whether an external deterministic observation is mandatory for actionability.

\subsection{Receipt verification}

Receipts declare an evidence \emph{role}: support or contradiction. A structural receipt names a repository-relative file, line interval, and expected source observation. A behavioral receipt additionally declares a command, expected exit code, required output marker, and falsification condition. The verifier rejects irrecoverable paths, malformed ranges, mismatched source, malformed commands, timeouts, unexpected exit status, or absent witness markers. For structural receipts only, a frozen conservative recovery can resolve an unambiguous fixture file or search that file when display-derived line numbers are stale; these recovery rules are fixed and deterministic. A failed receipt cannot be rescued by critic agreement.

The frozen evaluator includes two deterministic, non-model repair rules developed before Human PR 20: an AST result may flip a receipt's evidence role when the verifier explicitly observed the opposite role, and an inline-Python syntax failure may fall back from behavioral to structural verification. Both the original failure and repair event appear in the transcript. No free-form semantic repair is performed.

Verification is intentionally syntactic and operational rather than semantic. This avoids substituting a hidden judge model for the critic, but it creates two separate correctness questions: whether the receipt is mechanically valid and whether the verified observation actually bears on the claim. The experiments record both the verifier outcome and final critic decision so these surfaces remain distinguishable.

\subsection{Threat model and scope}

The failure of interest is \emph{false consensus}: reviewer and critic agree that an unsupported claim should be actionable. We do not assume malicious agents. The threat is correlated model error under plausible code-review language, incomplete context, or an attractive but irrelevant citation. The benchmark runner removes ground-truth labels and explanations from model-visible tasks. The verifier reads only the submitted receipt and fixture repository; it never reads the benchmark label.

Cases preserve the exact public comment URL, author, path, line, pull request, and commit. Each contains a focused changed-target excerpt and a companion changed-file excerpt when available, with less than 30 KB total context. This yields ten supported and ten unsupported cases.

\subsection{Temporal-pair construction}

The temporal design controls claim wording within each pair. At the reviewed commit, the human comment states a condition that is present in the code and the case is labeled supported. At the merge commit, the relevant code has changed such that the same claim is no longer supported. Pairing reduces wording and topic variation between labels, but it also means the two rows derived from one comment are statistically related. Bootstrap resampling therefore clusters on the source case identifier.

Selection required a public non-bot comment, an identifiable reviewed commit, a reconstructable merge state, a file-local claim, and a clear temporal contrast. These constraints improve provenance and auditability while excluding diffuse architectural comments, style preferences, and claims that require unavailable runtime systems. The benchmark is consequently a controlled slice of review reasoning, not a representative sample of all pull-request feedback.

\subsection{Study chronology and leakage control}

The chronology is part of the methodology. External PR 50 was frozen and evaluated first. Its receipt failures were inspected only after completion. Receipt-generation changes were then developed on Development PR 20, after which Human PR 20 was generated and frozen before its first model call. The original Human PR results were known before the GPT-5.6 model extension, so that extension is explicitly exploratory. No extension result is relabeled as a new untouched test.

The evaluator commit, prompts, configs, cases, and source excerpts were hashed before the first model call. Two model configurations each ran AR, AR-Text, and \evar-Hard once. Ground-truth fields are removed from the model-visible task object. Every attempted case produces a result row and transcript. A separate audit checks prompt hashes, transcript integrity, actionability gates, token counts, latency, and failures without calling a judge model.

\section{Metrics and Analysis}

For completed cases, false consensus rate and supported-claim retention are
\[
\fcr = \frac{\mathrm{unsupported\ actionable}}{\mathrm{unsupported\ completed}},\qquad
\scr = \frac{\mathrm{supported\ actionable}}{\mathrm{supported\ completed}}.
\]
Lower \fcr and higher \scr are desirable. Failures remain explicit and are excluded from both denominators. We report 10,000-sample bootstrap intervals, resampling by case identifier. Paired protocol deltas match model, replicate label, and case before resampling. These are descriptive intervals: the holdout is small and not a random sample from a defined population.

\subsection{Why two primary metrics}

Reporting only unsupported acceptance would reward a protocol that rejects every claim. Reporting only supported retention would reward one that accepts everything. The pair $(\fcr,\scr)$ exposes this tradeoff without collapsing it into a utility function whose error costs are unknown. A protocol dominates another only when it has no higher \fcr and no lower \scr, with at least one strict improvement. We use ``non-dominance'' when one metric improves while the other worsens or when outcomes tie.

\subsection{Paired uncertainty}

For two protocols $p$ and $q$, we compute case-matched differences $\Delta\fcr=\fcr_p-\fcr_q$ and $\Delta\scr=\scr_p-\scr_q$. Resampling preserves label balance through the eligible metric denominator and preserves temporal dependence through case clusters. Intervals describe sensitivity to the observed cases; they do not justify frequentist population claims because the benchmark is purposively constructed.

\subsection{Operational measurements and audit}

Every result row stores run status, model configuration, prompt hashes, verifier outcome, critic decision, final actionability, token counts, latency, and transcript path. The judge-free audit checks that each attempted case has one result and transcript, prompt hashes match the freeze, recorded token totals match model calls, durations are nonnegative, and final actionability obeys the protocol gate. API cost is reconstructed from recorded input/output tokens and the price frozen for each exact model. Failures remain explicit rows and are not silently converted into rejections.

\subsection{Development diagnostics versus held-out evidence}

Synthetic and small commit-grounded pilots were useful for finding implementation faults, including display-line cleanup, evidence-role inversion, path recovery, import-complete fixtures, evaluation-order checks, and brittle one-line witnesses. A post-hoc receipt-repair pass reached perfect scores on the inspected External PR 20 cases. That result is not counted as independent evaluation: those cases directly informed the repair. Its scientific role is diagnostic evidence that the harness can encode discovered checks, not evidence that those checks generalize.

\section{Discussion}

The final holdout changes the headline from a safety-retention tradeoff to non-dominance. The v2 receipt format solved much of the mechanical receipt-validity problem: 90\% of holdout receipts verified for each model. However, that did not improve decisions beyond text evidence. Receipt validity, evidentiary relevance, critic correctness, and final actionability are distinct failure surfaces.

The result does not show that \evar is inferior in a defined population. A one-case change moves either holdout metric by 0.100, and the intervals are correspondingly wide. It does show that requiring deterministic receipts is insufficient, by itself, to claim better review quality. The defensible benefit is procedural: every actionable \evar finding has an inspectable machine-checked receipt, and failed verification stops actionability.

The extension strengthens the non-dominance interpretation. Its three model tiers produce three different comparisons: a safety-retention exchange with Luna, equality with AR for Terra, and equality with AR-Text for Sol. Receipt verification rises from 85\% to 95\% without a monotonic improvement in final outcomes. Model behavior, receipt relevance, critic decisions, and verifier coverage jointly determine the operating point.

\subsection{Answers to the research questions}

\textbf{RQ1: decision quality.} Deterministic verification consistently changes the operating point but does not uniformly improve it. The first frozen study shows lower unsupported acceptance accompanied by supported-claim loss. The untouched human holdout shows equality or a small disadvantage relative to text evidence. The correct headline is non-dominance.

\textbf{RQ2: model sensitivity.} Receipt construction is strongly model-dependent, particularly in the earlier external study. Yet better receipt validity alone does not order final outcomes in the later extension. Verification should therefore be analyzed as an interaction among generator, critic, receipt language, and verifier rather than as a model-independent wrapper.

\textbf{RQ3: auditability.} The hard gate turns several otherwise latent failures into explicit artifacts: invalid JSON, absent paths, mismatched source, failing witnesses, verifier timeouts, and gate inconsistencies. This is the most robust positive result. It supports forensic review of why a finding became actionable even when aggregate accuracy does not improve.

\subsection{Design implications}

First, evidence interfaces should be treated as model-facing APIs. Schema complexity, path vocabulary, source formatting, and repair policy all affect whether a capable model can express what it knows. Second, verifier coverage should grow only on development data; adding targeted checks after inspecting a final holdout converts evaluation into diagnosis. Third, production systems need a policy for the abstention created by failed receipts. In safety-sensitive review, rejecting an unsupported claim may be valuable, but repeatedly suppressing valid findings can make the tool operationally irrelevant.

The results also caution against replacing a deterministic gate with a second semantic judge and calling the result verification. A learned judge may improve coverage, but it reintroduces correlated model error and makes the acceptance boundary harder to reproduce. A promising hybrid is to keep deterministic verification as a privileged signal while allowing a separate, explicitly reported ``unverified'' queue for claims requiring human or repository-scale analysis.

\subsection{What the study does not establish}

We do not show that \evar improves developer productivity, discovers more defects, or reduces review latency in practice. We do not estimate the relative cost of false positives and false negatives. We also do not claim that the five evaluated OpenAI models represent the broader model ecosystem. The frozen cross-provider extension is designed to address the last limitation, but its results must remain separate from the untouched holdout and cannot increase the number of independent benchmark cases.

\section{Threats to Validity}

\paragraph{Construct validity.}
FCR measures whether a pre-specified unsupported claim becomes actionable; it is not the false-positive rate of an open-ended review system. SCR measures retention of claims grounded in a public review-and-fix sequence; it does not establish that every retained comment is useful, well written, or worth a developer's attention. Mechanical receipt validity is likewise not semantic entailment. We report these constructs separately to avoid calling source matching ``correctness.''

\paragraph{Internal validity.}
Human PR 20 uses public review comments and subsequent code changes as temporal evidence. That reduces label ambiguity but does not eliminate it: a merge edit can address only part of a comment, and benchmark builders necessarily inspected every pair. We froze the evaluator before holdout calls, hid labels from prompts, clustered paired cases in the bootstrap, and retained failed calls. These controls reduce leakage and accounting bias; they do not replace independent expert adjudication.

\paragraph{External validity.}
Human PR 20 has ten source comments, five Python repositories, and ten cases per label. Selection requires a clean temporal contrast and reconstructable context, favoring localized and explicit claims. Results do not generalize to open-ended discovery, other languages, large architectural findings, or industrial review workflows. The focused excerpts also give models less context to search and less context to misunderstand than a full pull request.

\paragraph{Reliability and conclusion validity.}
API inference is stochastic, seeds are provenance labels, and most holdout cells have one call. With ten eligible cases per metric, one changed decision moves a rate by 0.100. Cluster bootstrap intervals describe sensitivity within this artifact, not a sampled population. The cross-provider gateway adds routing, throttling, and structured-output failures; incomplete cells are not used for performance claims. Behavioral witnesses run with \texttt{shell=False} and a timeout, but not inside an operating-system sandbox. The released cases are trusted frozen fixtures; executing receipts from untrusted models or repositories requires process isolation, network denial, and disposable filesystems.

\paragraph{Data ethics.}
The benchmark uses public GitHub repositories and public review comments, preserving URLs and usernames for provenance. It contains no private communication or inferred developer attributes. Public availability does not remove all ethical risk: comments were written for software maintenance, not research participation. The artifact therefore limits analysis to technical claims, avoids profiling individuals, and reports aggregate model behavior.

The model extension is exploratory and reuses Human PR 20 after the original outcomes were known. Its model calls are repeated measurements on the same cases, not additional independent benchmark examples, and there is only one call per model-protocol-case cell. Reasoning effort \texttt{none} controls the configuration but may understate maximum model capability. Model aliases, availability, behavior, and pricing can change after the freeze date.

The partial cross-provider extension introduces gateway routing as an additional construct. Exact model slugs are pinned, but the gateway may select among eligible serving providers. A common \texttt{low} reasoning-effort label does not imply identical hidden-compute budgets across vendors. Several cells are incomplete, and reuse of Human PR 20 prevents treating completed calls as new independent cases. We therefore report provider validity and failure accounting, not a cross-provider performance ranking.

The verifier is Python-specific and covers a limited set of structural and behavioral observations. Model aliases, provider routing, behavior, and pricing can change after the freeze date. These limitations motivate a larger, independently labeled and containerized replication rather than stronger claims from the present sample.

\section{Conclusion}

\evar makes reviewer-critic agreement necessary but insufficient: a claim must survive an external evidence check. In the earlier frozen experiment, this gate lowered unsupported actionability while rejecting supported claims. After receipt-generation improvements on a separate split, the final human-comment holdout achieved high receipt verification but no advantage over AR-Text. The exploratory three-model extension was heterogeneous rather than a universal win: \evar-Hard traded safety for retention with Luna, matched AR with Terra, and matched AR-Text with Sol. Mechanically checked evidence creates an auditable boundary, but a valid receipt is not synonymous with a correct review decision. A larger, independently labeled and preregistered evaluation is needed before making a population-level performance claim.

\section{Frozen Protocol Pseudocode}

\begin{verbatim}
input: candidate claim c, repository snapshot R
receipt = reviewer(c, R)          # one schema-constrained call

if protocol == AR:
    observation = NOT_USED
    decision = critic(c, receipt, observation)
elif protocol == AR_TEXT:
    text_evidence = project_text_fields(receipt)
    decision = critic(c, receipt, text_evidence)
else:                             # EVAR-Hard
    observation = deterministic_verify(receipt, R)
    receipt, observation = deterministic_repair_if_applicable(
        receipt, observation, R)
    decision = critic(c, receipt, observation)

actionable = (decision == ACCEPT)
if protocol == EVAR_HARD:
    actionable = actionable and observation == VERIFIED \
                 and receipt.role == SUPPORTS_CLAIM

emit result row and complete transcript
\end{verbatim}

The pseudocode elides bounded schema retry and error recording but preserves the configured acceptance semantics. Every protocol uses one reviewer and one critic call. AR-Text changes the evidence projection and critic prompt; \evar-Hard changes the verifier input, critic prompt, and final gate.

\section{Case and Output Schemas}

Each benchmark case is a JSON object with four field groups: identity and label; claim and family; repository snapshot and context paths; and source-comment provenance. The runner exposes only the task description, candidate claim, claim family, valid repository paths, and file contents to the model. Labels, snapshot kind, pairing, source-comment metadata, and construction evidence remain evaluator-only. Prompt-template SHA-256 hashes are recorded with every result; Appendix data files preserve the exact field names.

All three reviewer prompts use the same strict top-level schema: an object containing exactly one receipt. The receipt requires a claim identifier and text, evidence type and role, file, nullable line bounds, nullable verification command, nullable expected exit code, nullable expected-output substring, and a falsification condition. The schema rejects additional properties. A response that cannot be parsed after the configured retry becomes \texttt{ModelOutputError}; the evaluator does not synthesize a replacement.

\section{Interaction Schedule}

The configured protocols are matched at two model calls per case. The reviewer emits one receipt. AR calls the critic with a sentinel stating that external verification is unused. AR-Text constructs a textual-evidence view from the receipt and calls its evidence-aware critic prompt. \evar-Hard performs deterministic verification (and, when triggered, one deterministic repair and re-verification) before calling the critic. There is no model revision turn in the reported configured runs.

The runner records a call-level trace with request role, model slug, prompt hash, request start/end timestamps, token counts, response text, parser outcome, and retry number. A transcript is written even when the first call fails. This is useful in practice: invalid JSON, a valid JSON object with an empty receipt list, and a valid receipt that points at the wrong commit are different observations and should not collapse into one generic failure.

\section{Receipt Validation Rules}

Structural validation normalizes display artifacts such as Markdown fences, leading line numbers, and surrounding whitespace. It reads the requested file from the frozen snapshot and normally compares the normalized observation with the selected interval. Two conservative recovery paths are part of the frozen verifier: an unambiguous suffix, function-name, or sole-Python-file match can recover a stale structural path; and an interval extending beyond end-of-file can search the recovered file for the submitted observation. Behavioral receipts receive neither recovery. Behavioral validation parses the command into an argument vector, launches it with \texttt{shell=False} from the fixture directory, applies a five-second default timeout, and checks exit status plus a required \texttt{EVAR\_WITNESS\_PASS} marker. These controls prevent shell-pipeline interpretation and bound elapsed execution, but they do not prevent the child process from accessing the network or writing elsewhere under the evaluator's operating-system permissions. The verifier returns typed failure reasons for missing paths, wrong observations, exit mismatches, and timeouts. Generic successful structural recovery is deterministic but is not separately tagged, an auditability limitation for a future version.

The evidence role is checked independently of textual similarity. The evaluator performs only two frozen deterministic repairs: it aligns the role with an explicit opposite-role AST observation, or falls back from a syntactically invalid inline-Python behavioral witness to structural checking. Each repair is logged and re-verified. It does not rewrite claims, choose new files or ranges, or ask a model for semantic repair.

\section{Statistical and Cost Details}

FCR and SCR are computed after filtering to completed rows of the relevant ground-truth class. We report the numerator and denominator alongside each rate. Bootstrap intervals resample source case identifiers, not individual protocol rows, so the two temporal members of a human comment remain together. Paired deltas first join protocols on model, replicate, and case identifier and then resample those joined case clusters. A zero-width interval can occur for a metric that is identical in every resampled cluster; it is not evidence of large population certainty.

Token cost is computed from recorded input and output tokens and the price table frozen with each model configuration. Retries are included in cost and latency. Failed requests therefore consume budget and remain part of operational reporting even though they do not enter FCR/SCR denominators. The cross-provider table is restricted to validity accounting because gateway routing, model availability, and duplicate pilot attempts make a pooled quality estimate inappropriate.

\section{Representative Failure Cases}

The most common EVAR failure on the frozen external benchmark was not a verifier bug but a receipt that cited a nearby true line which did not establish the claim. Other examples included a command that passed but never printed the required marker, a line range copied from a display excerpt rather than the repository file, and a contradiction receipt submitted with the support role. On the cross-provider run, DeepSeek frequently returned an empty or non-JSON reviewer response after consuming its output budget; those rows are `ModelOutputError`, not negative review decisions. These examples explain why the paper reports receipt validity, critic decisions, and actionability as separate fields.

\section{What a Larger Replication Should Add}

The current design deliberately controls context and claim wording. A stronger replication should sample review comments before seeing their outcome, include complete pull-request snapshots, obtain two independent expert labels with adjudication, and preregister the sampling frame. It should also repeat each model-protocol cell, report calibration and abstention, and evaluate multilingual repositories. The present artifact supplies the receipt and audit machinery needed for that study; it should not be mistaken for evidence that 20 temporal cases represent the wider code-review population.

\section{Audit Invariants}

For each canonical run, the audit requires: (1) exactly one row for each attempted case; (2) a corresponding transcript; (3) model and protocol agreement between row and transcript; (4) frozen prompt hashes; (5) nonnegative latency; (6) call-level token totals equal to row totals; (7) failed runs contain a failure type and reason; and (8) \evar actionability implies both a verified receipt and critic acceptance. These checks do not judge semantic correctness; benchmark labels determine the reported metrics.
