\begin{abstract}
LLM reviewer and critic agents can converge on plausible but unsupported code-review findings when their interaction remains purely textual. We study Evidence-Verified Adversarial Review (\evar), a protocol that requires structured evidence receipts and deterministic verification before a finding can become actionable. After a 600-record frozen experiment exposed severe supported-claim loss, we improved receipt generation only on a separate development split, froze the evaluator, and evaluated once on Human PR 20: ten real human pull-request review comments paired across their reviewed and merge commits, producing 20 balanced cases from five previously unseen Python repositories. Across 120 audited decisions, \evar-Hard tied AR-Text with GPT-4.1-mini and trailed it with GPT-4.1. A pre-specified post-release extension added 180 audited decisions from GPT-5.6 Luna, Terra, and Sol at reasoning effort \texttt{none}. Descriptively pooled across those models, \evar-Hard scored \fcr{} 0.067 and \scr{} 0.700, versus 0.100/0.667 for AR-Text and 0.100/0.767 for AR, but model-level outcomes were heterogeneous and intervals were wide. \evar therefore does not demonstrate universal performance dominance. Its contribution is an auditable acceptance boundary and reproducible evidence that verification changes, rather than uniformly improves, the safety-retention operating point.
\end{abstract}

\section{Introduction}

Reviewer-critic systems use a second model call to challenge or refine a first model's answer. Iterative self-feedback and multi-agent debate can improve generation and reasoning \cite{selfrefine,debate}, but textual agreement is not independent evidence. In code review, two agents can converge on the same plausible interpretation of code while both overlook the observation that would falsify it.

\evar changes the acceptance rule. A reviewer submits a structured evidence receipt; a deterministic verifier checks a source location or executes a bounded witness; and only a verified receipt can become actionable. We ask whether that external gate reduces false consensus without suppressing supported findings.

We organize the study around three research questions:
\begin{description}
  \item[RQ1 (decision quality).] Does deterministic evidence verification reduce unsupported actionable findings without an unacceptable loss of supported findings?
  \item[RQ2 (model sensitivity).] Does the safety--retention operating point persist across model capability and cost tiers?
  \item[RQ3 (auditability).] Which protocol failures become mechanically observable when actionability requires a verified receipt?
\end{description}
These questions deliberately separate predictive performance from procedural assurance. A protocol can fail to dominate on \fcr and \scr while still making its acceptance path easier to inspect. Conversely, a high receipt-verification rate need not imply that the submitted evidence is relevant to the claim.

Our contributions are:
\begin{enumerate}
  \item a measurable definition of false consensus for candidate code-review claims;
  \item a structured receipt and deterministic actionability gate;
  \item a reproducible harness for matched AR, AR-Text, and \evar-Hard comparisons;
  \item frozen input and output manifests plus judge-free audits for 900 model decisions;
  \item a temporal holdout derived from human review comments across unseen repositories; and
  \item a mixed, non-dominance result across five models that separates the untouched study, exploratory extension, development, and post-hoc interpretation.
\end{enumerate}

\section{Related Work}

\subsection{Reflection, critique, and debate}

Self-Refine uses model-generated feedback to iteratively improve a model's output \cite{selfrefine}. Reflexion incorporates linguistic feedback into an episodic memory rather than updating model weights \cite{reflexion}. Multi-agent debate has similarly improved reasoning and factuality through textual deliberation \cite{debate}. These methods motivate the AR baselines but do not, by themselves, make agreement independent evidence. The same model family can reproduce a shared misconception across reviewer and critic roles.

Prior work also questions whether intrinsic self-correction is reliable without external feedback. CRITIC couples model critique to tool interactions and reports gains across question answering, program synthesis, and toxicity reduction \cite{critic}. \evar adopts the external-feedback premise but narrows both the task and the acceptance rule: the system judges a pre-specified code-review claim, and a deterministic receipt check is a necessary gate rather than optional context for another revision.

\subsection{Tool-using software-engineering agents}

SWE-agent shows that the interface between a model and a computer materially affects software-engineering performance \cite{sweagent}. Executable feedback can reveal failures that are invisible in a textual conversation, but unrestricted agent execution also introduces a large design surface. \evar uses a deliberately bounded interface: structural source checks or a verification command constrained by the benchmark fixture and verifier timeout. This restriction makes the acceptance boundary easier to audit, at the cost of incomplete coverage for repository-scale semantic claims.

\subsection{Automated code review and benchmarks}

CodeReviewer pre-trains on code changes and review activities, evaluating quality estimation, comment generation, and refinement \cite{codereviewer}. That line of work asks whether a system can generate or improve reviews. Our task begins later in the pipeline: a candidate claim already exists, and the system must decide whether the repository snapshot supports actionability.

Software-engineering benchmarks increasingly ground tasks in public development history. SWE-bench uses real GitHub issues and pull requests and demonstrates the need for repository context and executable environments \cite{swebench}. SWE-PRBench evaluates code-review models against pull-request feedback and reports limited detection of human-flagged issues \cite{sweprbench}. Our task is narrower: a candidate claim is given, and the system must decide whether it remains actionable under the supplied repository snapshot.

\section{Protocols}

All protocols receive the same candidate claim, task description, repository context, model configuration, and interaction budget.

\begin{table}[h]
\centering
\caption{Compared protocols.}
\label{tab:protocols}
\begin{tabularx}{\linewidth}{@{}lXX@{}}
\toprule
Protocol & Evidence handling & Actionability gate \\
\midrule
AR & Reviewer proposes a finding; critic evaluates textually. & Critic returns \texttt{ACCEPT}. \\
AR-Text & Reviewer adds textual evidence when challenged. & Critic returns \texttt{ACCEPT}. \\
\evar-Hard & Reviewer submits a receipt; verifier checks structural or behavioral evidence. & Verifier returns \texttt{VERIFIED} and critic returns \texttt{ACCEPT}. \\
\bottomrule
\end{tabularx}
\end{table}

An \evar receipt contains the claim, evidence type and role, file and line range, optional verification command, expected observation, and falsification condition. Structural evidence is accepted only by exact source matching after conservative cleanup of display-only line numbers and Markdown fences. Behavioral witnesses must exit successfully and print a designated pass marker only when the claim is supported. The verifier does not use semantic fuzzy matching or model judgment.

\subsection{Actionability semantics}

Let $c$ be a candidate claim, $d\in\{\texttt{ACCEPT},\texttt{REJECT}\}$ the critic decision, and $v\in\{\texttt{VERIFIED},\texttt{FAILED}\}$ the verifier outcome. The final gates are
\[
A_{\mathrm{AR}}(c)=\mathbf{1}[d=\texttt{ACCEPT}],\qquad
A_{\mathrm{EVAR}}(c)=\mathbf{1}[d=\texttt{ACCEPT}\land v=\texttt{VERIFIED}].
\]
AR-Text shares the AR gate but supplies textual evidence to the critic. The distinction is therefore not whether evidence appears in the dialogue; it is whether an external deterministic observation is mandatory for actionability.

\subsection{Receipt verification}

Receipts declare an evidence \emph{role}: support or contradiction. A structural receipt names a repository-relative file, line interval, and expected source observation. A behavioral receipt additionally declares a command, expected exit code, required output marker, and falsification condition. The verifier rejects missing paths, invalid ranges, mismatched source, malformed commands, timeouts, unexpected exit status, or absent witness markers. A failed receipt cannot be rescued by critic agreement.

Verification is intentionally syntactic and operational rather than semantic. This avoids substituting a hidden judge model for the critic, but it creates two separate correctness questions: whether the receipt is mechanically valid and whether the verified observation actually bears on the claim. The experiments record both the verifier outcome and final critic decision so these surfaces remain distinguishable.

\subsection{Threat model and scope}

The failure of interest is \emph{false consensus}: reviewer and critic agree that an unsupported claim should be actionable. We do not assume malicious agents. The threat is correlated model error under plausible code-review language, incomplete context, or an attractive but irrelevant citation. The benchmark runner removes ground-truth labels and explanations from model-visible tasks. The verifier reads only the submitted receipt and fixture repository; it never reads the benchmark label.

External PR 50 contains 50 balanced claims grounded in 25 commits from Click, pluggy, attrs, more-itertools, and Requests. Its 600 model decisions exposed a false-consensus versus retention tradeoff and motivated receipt-generation work. No code or prompt change was evaluated against that benchmark again.

Human PR 20 was created after v2 development. Ten comments by non-bot GitHub reviewers were selected from Black, pytest, Rich, Pydantic, and Poetry, none of which appeared in External PR 50. Each comment yields a temporal pair: the reviewed commit supports the claim and the merged commit no longer does. Cases preserve the exact public comment URL, author, path, line, pull request, and commit. Each contains a focused changed-target excerpt and a companion changed-file excerpt when available, with less than 30 KB total context. This yields ten supported and ten unsupported cases.

\subsection{Temporal-pair construction}

The temporal design controls claim wording within each pair. At the reviewed commit, the human comment states a condition that is present in the code and the case is labeled supported. At the merge commit, the relevant code has changed such that the same claim is no longer supported. Pairing reduces wording and topic variation between labels, but it also means the two rows derived from one comment are statistically related. Bootstrap resampling therefore clusters on the source case identifier.

Selection required a public non-bot comment, an identifiable reviewed commit, a reconstructable merge state, a file-local claim, and a clear temporal contrast. These constraints improve provenance and auditability while excluding diffuse architectural comments, style preferences, and claims that require unavailable runtime systems. The benchmark is consequently a controlled slice of review reasoning, not a representative sample of all pull-request feedback.

\subsection{Study chronology and leakage control}

The chronology is part of the methodology. External PR 50 was frozen and evaluated first. Its receipt failures were inspected only after completion. Receipt-generation changes were then developed on Development PR 20, after which Human PR 20 was generated and frozen before its first model call. The original Human PR results were known before the GPT-5.6 model extension, so that extension is explicitly exploratory. No extension result is relabeled as a new untouched test.

The evaluator commit, prompts, configs, cases, and source excerpts were hashed before the first model call. Two model configurations each ran AR, AR-Text, and \evar-Hard once. Ground-truth fields are removed from the model-visible task object. Every attempted case produces a result row and transcript. A separate audit checks prompt hashes, transcript integrity, actionability gates, token counts, latency, and failures without calling a judge model.

After the original Human PR 20 study was released, we specified an exploratory model extension before making its benchmark calls. The unchanged cases, prompts, verifier semantics, scoring, and budgets were evaluated once per protocol with GPT-5.6 Luna, Terra, and Sol. All configurations used explicit reasoning effort \texttt{none}; seed 41 is a provenance label rather than a deterministic inference control. A transport-only backend change omitted the unsupported \texttt{temperature} field for these models. The evaluator and three configurations were frozen before evaluation.

\subsection{Exploratory cross-provider extension}

We also ran a pre-specified exploratory extension through OpenRouter, holding cases, prompts, budgets, verifier semantics, and scoring fixed. The completed blocks cover Claude Sonnet 5 and Gemini 3.1 Pro Preview (20 cases under each of AR, AR-Text, and \evar-Hard; 120/120 successful rows). DeepSeek V4 Pro completed 20 AR cases (11 valid, 9 invalid-output failures) and 17 AR-Text cases before the run was stopped; Kimi K3 completed 16 AR cases plus a separate three-case pilot, and Qwen3.8 Max completed a three-case AR pilot. These rows are exploratory and are not pooled as independent evidence. Invalid model outputs and incomplete cells are retained as failures rather than silently excluded. The OpenRouter transport uses a process-level curl deadline because some chunked responses otherwise remained open indefinitely.

\section{Metrics and Analysis}

For completed cases, false consensus rate and supported-claim retention are
\[
\fcr = \frac{\mathrm{unsupported\ actionable}}{\mathrm{unsupported\ completed}},\qquad
\scr = \frac{\mathrm{supported\ actionable}}{\mathrm{supported\ completed}}.
\]
Lower \fcr and higher \scr are desirable. Failures remain explicit and are excluded from both denominators. We report 10,000-sample bootstrap intervals, resampling by case identifier. Paired protocol deltas match model, replicate label, and case before resampling. These are descriptive intervals: the holdout is small and not a random sample from a defined population.

\subsection{Why two primary metrics}

Reporting only unsupported acceptance would reward a protocol that rejects every claim. Reporting only supported retention would reward one that accepts everything. The pair $(\fcr,\scr)$ exposes this tradeoff without collapsing it into a utility function whose error costs are unknown. A protocol dominates another only when it has no higher \fcr and no lower \scr, with at least one strict improvement. We use ``non-dominance'' when one metric improves while the other worsens or when outcomes tie.

\subsection{Paired uncertainty}

For two protocols $p$ and $q$, we compute case-matched differences $\Delta\fcr=\fcr_p-\fcr_q$ and $\Delta\scr=\scr_p-\scr_q$. Resampling preserves label balance through the eligible metric denominator and preserves temporal dependence through case clusters. Intervals describe sensitivity to the observed cases; they do not justify frequentist population claims because the benchmark is purposively constructed.

\subsection{Operational measurements and audit}

Every result row stores run status, model configuration, prompt hashes, verifier outcome, critic decision, final actionability, token counts, latency, and transcript path. The judge-free audit checks that each attempted case has one result and transcript, prompt hashes match the freeze, recorded token totals match model calls, durations are nonnegative, and final actionability obeys the protocol gate. API cost is reconstructed from recorded input/output tokens and the price frozen for each exact model. Failures remain explicit rows and are not silently converted into rejections.

\subsection{Receipt validity and decision quality}

The studies show that receipt validity and final quality are not interchangeable. In the first frozen external experiment, GPT-4.1 produced 76 verified receipts per 100 attempts while GPT-4.1-mini produced 47 among 99 completed attempts; their supported retention differed accordingly. After v2 development, both original Human PR models verified 18 of 20 receipts, yet \evar-Hard did not improve on AR-Text. In the GPT-5.6 extension, receipt validity rose from 17/20 for Luna to 19/20 for Sol without monotonic improvement in either primary metric.

\subsection{Development diagnostics versus held-out evidence}

Synthetic and small commit-grounded pilots were useful for finding implementation faults, including display-line cleanup, evidence-role inversion, path recovery, import-complete fixtures, evaluation-order checks, and brittle one-line witnesses. A post-hoc receipt-repair pass reached perfect scores on the inspected External PR 20 cases. That result is not counted as independent evaluation: those cases directly informed the repair. Its scientific role is diagnostic evidence that the harness can encode discovered checks, not evidence that those checks generalize.

\section{Discussion}

The final holdout changes the headline from a safety-retention tradeoff to non-dominance. The v2 receipt format solved much of the mechanical receipt-validity problem: 90\% of holdout receipts verified for each model. However, that did not improve decisions beyond text evidence. Receipt validity, evidentiary relevance, critic correctness, and final actionability are distinct failure surfaces.

The result does not show that \evar is inferior in a defined population. A one-case change moves either holdout metric by 0.100, and the intervals are correspondingly wide. It does show that requiring deterministic receipts is insufficient, by itself, to claim better review quality. The defensible benefit is procedural: every actionable \evar finding has an inspectable machine-checked receipt, and failed verification stops actionability.

The extension strengthens the non-dominance interpretation. Its three model tiers produce three different comparisons: a safety-retention exchange with Luna, equality with AR for Terra, and equality with AR-Text for Sol. Receipt verification rises from 85\% to 95\% without a monotonic improvement in final outcomes. Model behavior, receipt relevance, critic decisions, and verifier coverage jointly determine the operating point.

\subsection{Answers to the research questions}

\textbf{RQ1: decision quality.} Deterministic verification consistently changes the operating point but does not uniformly improve it. The first frozen study shows lower unsupported acceptance accompanied by supported-claim loss. The untouched human holdout shows equality or a small disadvantage relative to text evidence. The correct headline is non-dominance.

\textbf{RQ2: model sensitivity.} Receipt construction is strongly model-dependent, particularly in the earlier external study. Yet better receipt validity alone does not order final outcomes in the later extension. Verification should therefore be analyzed as an interaction among generator, critic, receipt language, and verifier rather than as a model-independent wrapper.

\textbf{RQ3: auditability.} The hard gate turns several otherwise latent failures into explicit artifacts: invalid JSON, absent paths, mismatched source, failing witnesses, verifier timeouts, and gate inconsistencies. This is the most robust positive result. It supports forensic review of why a finding became actionable even when aggregate accuracy does not improve.

\subsection{Design implications}

First, evidence interfaces should be treated as model-facing APIs. Schema complexity, path vocabulary, source formatting, and repair policy all affect whether a capable model can express what it knows. Second, verifier coverage should grow only on development data; adding targeted checks after inspecting a final holdout converts evaluation into diagnosis. Third, production systems need a policy for the abstention created by failed receipts. In safety-sensitive review, rejecting an unsupported claim may be valuable, but repeatedly suppressing valid findings can make the tool operationally irrelevant.

The results also caution against replacing a deterministic gate with a second semantic judge and calling the result verification. A learned judge may improve coverage, but it reintroduces correlated model error and makes the acceptance boundary harder to reproduce. A promising hybrid is to keep deterministic verification as a privileged signal while allowing a separate, explicitly reported ``unverified'' queue for claims requiring human or repository-scale analysis.

\subsection{What the study does not establish}

We do not show that \evar improves developer productivity, discovers more defects, or reduces review latency in practice. We do not estimate the relative cost of false positives and false negatives. We also do not claim that the five evaluated OpenAI models represent the broader model ecosystem. The frozen cross-provider extension is designed to address the last limitation, but its results must remain separate from the untouched holdout and cannot increase the number of independent benchmark cases.

\section{Threats to Validity}

Human PR 20 has only ten source comments, five repositories, and ten cases per label. Selection requires a clean temporal contrast and reconstructable context, favoring localized and explicit claims. Temporal pairs are related rather than independent. Ground truth follows the public review comment and subsequent code change but lacks independent expert adjudication. Benchmark builders inspected source comments to validate provenance and label direction, although evaluator tuning stopped before the frozen run. A public independent methodology review has been requested but was not complete at release time.

The model extension is exploratory and reuses Human PR 20 after the original outcomes were known. Its model calls are repeated measurements on the same cases, not additional independent benchmark examples, and there is only one call per model-protocol-case cell. Reasoning effort \texttt{none} controls the configuration but may understate maximum model capability. Model aliases, availability, behavior, and pricing can change after the freeze date.

The pending cross-provider extension introduces gateway routing as an additional construct. Exact model slugs are pinned, but the gateway may select among eligible serving providers. A common \texttt{low} reasoning-effort label does not imply identical hidden-compute budgets across vendors. One call per cell is vulnerable to sampling variation, and reuse of Human PR 20 prevents treating the additional 300 decisions as new independent cases.

The task evaluates pre-specified candidate claims, not end-to-end defect discovery or review utility. Focused excerpts omit repository-scale dependency graphs. The verifier is Python-specific and covers a limited set of structural and behavioral observations. API calls are not guaranteed deterministic; integer seeds are provenance labels. Model behavior and pricing can change. Finally, bootstrap intervals quantify resampling variability inside this artifact, not representativeness of software review in general.

\section{Reproducibility and Availability}

Release \texttt{v0.2.0} contains evaluator code, prompts, configs, benchmark snapshots, all 720 original canonical decisions and transcripts, input and output manifests, audit reports, analysis scripts, and the independent-review packet. The 180-decision GPT-5.6 extension is prepared locally for a later revision and is not part of that public release; its input freeze, run index, report, audit, transcripts, and results manifest preserve the extension artifact. The public repository and project site are available at
\begin{center}
\url{https://github.com/kishormorol/evar}\\
\url{https://evar-research.elitelab-ai.chatgpt.site}
\end{center}
The release notes provide the archival DOI when the Zenodo deposit is complete.

The artifact has four layers. Input manifests hash cases, repository snapshots, prompts, model configs, evaluator code, verifier code, and scoring code. Run indices identify canonical JSONL outputs. Judge-free audit reports check completeness and invariants. Output manifests hash every canonical result and transcript. The cross-provider input manifest additionally freezes the gateway endpoint, exact model slugs, reasoning setting, token cap, and schema-routing requirement.

The core deterministic reproduction path is:
\begin{verbatim}
python -m unittest discover -s tests
python -m evar.preflight --config CONFIG --cases CASES
python -m evar.run --protocol PROTOCOL --cases CASES \
  --config CONFIG --output-dir RESULTS
\end{verbatim}
Model-backed reproduction requires the corresponding API credential and will not be byte-identical because provider inference is not guaranteed deterministic. The preserved transcripts and metadata support outcome-level rather than bit-level replication.

\section{Conclusion}

\evar makes reviewer-critic agreement necessary but insufficient: a claim must survive an external evidence check. In the earlier frozen experiment, this gate lowered unsupported actionability while rejecting supported claims. After receipt-generation improvements on a separate split, the final human-comment holdout achieved high receipt verification but no advantage over AR-Text. The exploratory three-model extension was heterogeneous rather than a universal win: \evar-Hard traded safety for retention with Luna, matched AR with Terra, and matched AR-Text with Sol. Mechanically checked evidence creates an auditable boundary, but a valid receipt is not synonymous with a correct review decision. A larger, independently labeled and preregistered evaluation is needed before making a population-level performance claim.

\section{Frozen Protocol Pseudocode}

\begin{verbatim}
input: candidate claim c, repository snapshot R
review = reviewer(c, R)
challenge = critic(review, c, R)
revision = reviewer(review, challenge, c, R)

if protocol == AR or protocol == AR_TEXT:
    actionable = (critic(revision, c, R) == ACCEPT)
else:
    receipt = parse_structured_receipt(revision)
    observation = deterministic_verify(receipt, R)
    decision = critic(revision, observation, c, R)
    actionable = (observation == VERIFIED and decision == ACCEPT)

emit result row and complete transcript
\end{verbatim}

\section{Audit Invariants}

For each canonical run, the audit requires: (1) exactly one row for each attempted case; (2) a corresponding transcript; (3) model and protocol agreement between row and transcript; (4) frozen prompt hashes; (5) nonnegative latency; (6) call-level token totals equal to row totals; (7) failed runs contain a failure type and reason; and (8) \evar actionability implies both a verified receipt and critic acceptance. These checks do not judge semantic correctness; benchmark labels determine the reported metrics.
